# Verified vs unverified (read before the viva)

## Verified here (macOS 14.8 Intel, Xcode 16.2)
- `BuildSightKit` compiles and **142 Swift Testing tests pass** (`scripts/run-kit-tests.sh`). A deliberate break of the flag threshold made tests fail, confirming the runner reports failures.
- Core Data store (real SQLite file, reopened), sync engine against a scripted backend, REST client against a stubbed transport, session/biometric state machine against fakes, view models against real stores.
- The Core ML + Vision path loads the converted model and runs it (macOS, Intel laptop): a synthetic image produced no detections and 168 ms inference. The new five-class PPE model also loads through `CoreMLHelmetAnalyzer` and returns "unable to assess" on a plain wallpaper image. **Those are smoke tests, not accuracy or phone-speed measurements.**
- The SwiftUI layer type-checks against the macOS SDK (`scripts/typecheck-app.sh`) with a small shim. iOS-only files are excluded.

## NOT verified
- **The app has never been through a full Xcode build or run in a simulator or on a device.** What *was* checked with Xcode 16.2's compiler against the iOS 18.2 simulator SDK: `BuildSightKit` compiles for iOS; the app target (26 files, including `CameraService`, `QRScannerView`, `KeychainSessionStore`, `BiometricService`, `LocationService`) and the widget type-check with 0 errors; a deliberately broken file fails the same check; the package's 142 tests pass under Xcode's SwiftPM. **Not checked:** linking, asset catalogs, Info.plist and entitlements processing, code signing, widget embedding, Core ML model compilation, and any run. `xcodebuild` cannot start until the iOS simulator platform (a separate ~7-8 GB download) is installed or a real device is the destination.
- **No live backend test.** A Supabase project exists and its URL and publishable key are in the git-ignored `Config/Secrets.xcconfig`, and `schema.sql` was applied to it (5 tables with row-level security, 8 policies, 3 functions, private `evidence` bucket confirmed by querying the catalogue), and it is seeded with one demo project (3 site areas) and six confirmed test users (supervisor, project manager x2, inspector, engineer, site worker; membership, profile and team rows read back and consistent). `scripts/backend-smoke.sh` has been run live as the supervisor user and passed 9/9: password sign-in, wrong-credential refusal, profile with organisation embed, membership, reading the seeded rows, direct insert into `records` refused (403), `upsert_record` present and refusing reference-data writes, anon key sees nothing. **Not yet verified live:** a successful `upsert_record` write, replay and version-conflict handling on the server, evidence photo upload, the app's own sync code, and the other roles. What *is* verified: `Backend/supabase/test_schema.sh` runs the schema on a local PostgreSQL (Supabase's auth/storage replaced by stand-ins) and 27 access-rule checks pass, including a mutation check; the project's auth endpoint answers wrong credentials with the 400 `invalid_credentials` the client maps. PostgREST, JWT handling and Realtime remain untested. REST shapes follow Supabase's documented API but are untested against a server (tests use a stub).
- **Phone-photo accuracy is unmeasured.** The five-class PPE model has held-out test numbers from its own datasets' test splits (below), but those splits come from the same sources as the training data. There are no results on real phone photos from a site. The older helmet-only model has no measured numbers at all.
- **PPE model results (held-out test splits, `ML/models/provenance_ppe.json`).** On Construction-PPE's 141 test images (the only set with all five classes): helmet AP50 0.90, vest 0.87, gloves 0.75, **no-helmet 0.12, no-gloves 0.09**, overall mAP50 0.55. On a 1,234-image Roboflow test split (helmet/vest/gloves only): mAP50 0.71 (helmet 0.76, vest 0.83, gloves 0.53). The two "no-" classes miss about 8 in 10 real cases and are wrong about 3 in 4 times they fire, so they must only be reviewer hints. Missing-helmet detection is likely **worse** than with the older helmet-only model, which was trained on far more bare-head examples.
- **Licence of the PPE model is unresolved.** Training data includes an AGPL-3.0 dataset (Construction-PPE) and the Roboflow set is CC BY 4.0; Ultralytics YOLOv8 is AGPL-3.0. The weights are git-ignored and not cleared for redistribution.
- No VoiceOver, Dynamic Type, touch-target or reduced-motion testing on a device. Contrast is checked by unit test for the token colours only.
- Widget refresh, App Group sharing, deep links from the widget, MapKit rendering and offline tile behaviour: untested. Offline map imagery is **not** claimed.

## Not implemented
- **Remote push notifications** (needs an Apple Developer account, APNs key and a server that sends pushes). The in-app Notifications tab and local reminders exist. The proposal lists Push Notifications, so confirm with your lecturer which mandatory pair you are claiming (Core Data + Face ID is the safe baseline).
- **Realtime channel.** Other devices see changes on the next pull (foreground, connectivity, Sync Now), not live. Supabase Realtime is enabled in the schema but the client does not subscribe.
- **Not detected:** a *missing* vest (the model has no no-vest class, so no vest box proves nothing), harnesses and fall protection, hearing and eye protection, respirators. Vests and gloves are reported only when seen. Worker identity recognition is deliberately never built.
- Photo attachment to inspection items and issue drafts from the camera is modelled (`photoIDs`) but the UI does not yet offer an "attach photo" button on those screens.
- Daily report export, before/after comparison, marker clustering (proposal "future enhancements").

## Decisions that differ from the proposal (record and justify in the report)
- **No "site safety score".** Replaced with defined counts (unreviewed / confirmed / dismissed flags). A single score would read as an objective safety measure.
- **PPE scope.** Started helmet-only (your instruction), later extended to helmet, vest and gloves on a five-class model. Vests and gloves never raise issues by themselves; "no gloves" is a hint only. Record this as a scope change; do not claim lecturer approval unless you have it in writing.
- **Widget** is a proposal commitment but not in the lecturer's approved advanced list in your scan (Core ML, MapKit/Core Location; third slot blank). Ask whether it counts.
- **Light appearance only**, matching the prototype's sunlight-readability palette. Dark mode is a possible accessibility trade-off to discuss.
